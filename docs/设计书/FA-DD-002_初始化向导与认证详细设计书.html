1. 概要

1.1 目的

让部署方只需提供一个数据库连接串就能启动服务，其余配置（管理员、品牌、大模型、渠道）在浏览器里一次完成并存入 PostgreSQL；完成后后台以用户名密码登录保护。

1.2 范围

初始化口令、五步向导、初始化提交的原子性；登录 / 登出 / 当前用户 / 改密；前端的分流与登录跳转。多管理员与角色不在一期范围。

1.3 相关文档

FA-DD-001（整体架构）、FA-DD-007（设置分区字段）。

1.4 用语定义

用语定义
初始化口令（setupCode）未初始化时进程启动生成的 8 位数字，只打印在服务端日志，仅本次进程有效
会话 token32 字节随机数的 hex，放在 httpOnly cookie zw_session；库里只存 SHA-256

2. 前提

2.1 系统构成

浏览器 → Next（rewrites）→ Go /api/setup/*、/api/auth/*。同源访问，cookie 不跨域。

2.2 技术要素

  • 密码 bcrypt（DefaultCost）；token crypto/rand；会话 TTL 14 天。
  • 登录限速：进程内按 IP 计数，连续失败 5 次锁 15 分钟。gin TrustedProxies 只信任回环地址（Next 反代）。

2.3 前提条件・制约事项

  • 为什么要口令：未初始化的实例谁先打开向导谁就是管理员。口令只出现在服务器日志里，能看到日志 ≈ 能管理这台服务器，不需要额外 env。
  • 口令每次启动重新生成；初始化完成后不再生成，/api/setup/llm-test 与 /api/setup/complete 永久返回 409。
  • 一期只有一个管理员（向导创建）。忘记密码需在库里删掉 admin_users 全部行并把 system_settings.setup 置为未完成后重启，重新走向导（二期提供 CLI 重置）。

4. 功能详细

4.1 向导步骤（F-03 前端）

步骤内容本地校验
1 初始化口令说明口令来源（日志里的 setupCode=…）8 位数字
2 管理员账号用户名（缺省 admin）、密码、确认用户名 ≥3；密码 ≥8；两次一致
3 品牌信息名称、一句话简介、官网链接名称必填
4 大模型预设（OpenAI / DeepSeek / 通义千问 / Anthropic）、协议、模型、Base URL、API Key、温度、最大输出、超时；「测试连接」Base URL、Key、模型必填（不强制测试通过）
5 接入渠道QQ 机器人与 Telegram 表单（均可关闭跳过）；企业微信提示预留启用时凭据必填

口令错误不会在第 1 步立即发现（口令只在提交接口校验），第 4 步「测试连接」或最终提交时才返回 403——避免给口令一个无代价的枚举接口。

4.2 提交初始化（F-03 服务端）

请求体：{admin:{username,password}, brand, llm, qqbot, telegram}。

  1. S-01 requireSetupPending：已完成 → 409；X-Setup-Code 不等于进程口令 → 403。
  2. S-02 用户名去空白后校验 3~32 字符、密码 8~72 字节（bcrypt 上限 72）；品牌名称非空。
  3. S-03 以 settings.Defaults() 为底覆盖提交的分区，settings.Validate 全量校验（规则见 FA-DD-007）。
  4. S-04 store.CompleteSetup 单事务：LOCK TABLE admin_users IN EXCLUSIVE MODE → 条件插入（WHERE NOT EXISTS (SELECT 1 FROM admin_users)）→ 写入全部分区 → 写 setup={"completed":true}。插入 0 行 → 409（两个浏览器同时提交只有一个成功）。
  5. S-05 重新 Settings.Load 并 runtime.Apply：此刻起渠道开始连接。
  6. S-06 前端提示后跳 /login。
sequenceDiagram
  participant B as 浏览器
  participant S as Go
  participant DB as PG
  B->>S: POST /api/setup/complete (X-Setup-Code)
  S->>S: 口令 / 字段 / Validate
  S->>DB: BEGIN; LOCK admin_users; INSERT … WHERE NOT EXISTS
  S->>DB: UPSERT system_settings × N; setup.completed=true; COMMIT
  S->>S: Settings.Load + runtime.Apply
  S-->>B: {"completed":true}

4.3 登录（F-04）

  1. S-01 IP 已锁定 → 429。
  2. S-02 按用户名查；不存在时也对固定哑哈希跑一次 bcrypt，两种失败耗时一致，防按响应时间枚举用户名。
  3. S-03 记录成功 / 失败（成功清零）；失败 → 401。
  4. S-04 生成 token，admin_sessions 插入 SHA-256(token) + 过期时间，刷新 last_login_at，顺手删除过期会话。
  5. S-05 下发 cookie：HttpOnly; SameSite=Lax; Path=/; Max-Age=14d；请求为 TLS 或 X-Forwarded-Proto: https 时加 Secure。

4.4 鉴权中间件与改密（F-06/F-07）

  • requireAdmin：无 cookie → 401 未登录；token 哈希查不到或过期 → 401 登录已过期，请重新登录。
  • 改密：校验原密码 → 新密码规则同初始化 → 更新哈希并删除该用户全部会话（含当前），前端跳登录页。

4.5 前端分流（F-08）

  • /：查 setup 状态，未完成去 /setup，否则 /admin。
  • /admin/* 布局：先查 setup（未完成去向导），再 GET /api/auth/me；拿到用户前只渲染骨架屏。
  • lib/api.ts：任意请求 401（登录接口自身除外）→ 硬跳转 /login?redirect=当前路径，清空内存态；登录成功后只接受以 / 开头且不以 // 开头的 redirect（防开放重定向）。

4.6 异常系

  • E-01 口令错误：403，向导停留当前步，toast 提示。
  • E-02 初始化后再访问 /setup：页面查到 completed 自动跳 /login；直接调接口 409。
  • E-03 初始化提交成功但 Apply 时渠道连接失败：不影响初始化结果，渠道状态在总览显示错误并后台重试。

7. 配置项

无 env。会话 TTL（14 天）、限速阈值（5 次 / 15 分钟）为代码常量（auth.go）。
