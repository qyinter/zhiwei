1. 概要

1.1 目的

客服群里不是每个问题都有人 @ 机器人。群运营让机器人在群里多做几件事：提问长时间没人答时谨慎补位、新成员入群时打招呼、按业务规则自动审批入群申请、统计大家最常问的问题；每个群可以单独开关这些功能。

1.2 范围

群消息时间线（主动回复、反思沉淀、问题排行共用的素材）、主动回复扫描器、可答性判断、入群欢迎、入群审核与处理记录、按群设置、问题排行，以及后台「群管理」「问题排行」「主动回复」「入群审核」页。反思沉淀见 FA-DD-009。

1.3 相关文档

FA-DD-003（事件与订阅位）、FA-DD-004（客服推理、主动模式）、FA-DD-009（反思沉淀）。

1.4 用语定义

用语定义
群时间线group_messages：按群组织的全部群消息（含未 @ 机器人的），带发言人角色
客服发言角色为 owner（群主）或 admin（管理员）的群消息
静默阈值提问后经过多久仍无人应答才考虑补位（proactive.silenceSec）
游标poller_cursors 中按群记录的扫描进度，key = proactive:{channel}:{chatId}、topic:{channel}:{chatId}、topic:private
群策略groups.policies[] 中某个群的单独设置；字段为 null 表示跟随全局
主题问题排行里的一类问题（question_topics），由模型归类时新建或归入

2. 前提

2.1 系统构成

入站事件经编排器 Handle 分流：入群事件 → 欢迎；入群申请 → 审核（独立 goroutine）；群消息 → 写时间线，只有 @ 机器人的继续走问答流程。主动回复是独立后台循环 RunProactive，每轮重新读取设置，改设置无需重启。

2.2 技术要素

  • 可答性判断与后台结构化调用统一走 askJSON：一次无工具、无历史的调用，system 恒定、数据在 user 侧、宽松解析首个 {…}；每次调用记 llm_calls.purpose（judge / reflect / compact / promote）。
  • QQ 群成员事件订阅位 GROUP_MEMBER_EVENT (1<<24)，只在入群欢迎或入群审核开启时订阅（未开通权限时订阅会被网关拒绝）。

2.3 前提条件・制约事项

  • 主动回复需要全量群消息：QQ 需在开放平台开通「接收所有消息」并打开设置 channel.qqbot.groupAll；TG 需在 BotFather 关闭 privacy mode。否则时间线里只有 @ 消息，扫描器没有候选。
  • QQ 补位回复走被动回复（静默阈值缺省 180 秒，在 5 分钟窗口内）；超窗自动改发主动消息（FA-DD-003）。
  • QQ 入群事件 GROUP_MEMBER_ADD 不支持被动回复（event_id 只支持 INTERACTION_CREATE / GROUP_ADD_ROBOT / GROUP_MSG_RECEIVE），欢迎语走主动消息，计入单群每天 1000 条额度。
  • QQ 入群事件不带昵称；成员信息接口 GET /v2/groups/{group}/members/{member} 目前仅白名单机器人可用（错误码 11253），因此昵称取「同一用户最近出现过的昵称」，再取不到用「新朋友」。
  • 入群申请事件只有机器人是群管理员时才会推送；审批接口 60 QPM。入群审核只支持 QQ。
  • 群白名单（agent.allowAllChats / chats）同时约束时间线写入、主动回复、欢迎、审核与问题排行；群策略只在白名单内的群生效。

4. 功能详细

4.1 群时间线写入（F-01）

  1. S-01 群 / 频道消息先过群白名单，不在白名单直接丢弃。
  2. S-02 不带图片的整句命令（重置 / 帮助 / 人工）→ 不写。带图片的消息正文后追加占位「[图片]」（多张为「[图片×N]」），只有图片的写占位；正文与图片都没有 → 不写。时间线只存文字，图片本身不下载（FA-DD-004 4.12）。
  3. S-03 写入 (channel, chat_type, chat_id, user_id, user_name, role, content, platform_msg_id, mentioned)。同一平台消息重复投递只合并 mentioned = 旧值 OR 新值：QQ 全量模式下同一条 @ 消息会以 GROUP_MESSAGE_CREATE 与 GROUP_AT_MESSAGE_CREATE 各推一次，前者可能识别不出 @。
  4. S-04 未 @ 机器人的消息到此结束；@ 机器人的继续走 FA-DD-004 问答流程。
  5. 角色来源：QQ 取事件 author.member_role；TG 取 getChatAdministrators（creator → owner、administrator → admin，按群缓存 10 分钟，失败也缓存空表）。
  6. 保留：群时间线保留 回看窗口 + 静置阈值（且至少 1 天），清理在反思循环中执行，与反思开关无关；主动回复记录保留 90 天。

4.2 主动回复（F-02）

flowchart TD
  T[每 scanSec 秒] --> C{群在白名单且渠道在线}
  C -->|否| X[跳过]
  C -->|是| K{有游标}
  K -->|否 冷启动| S0[游标 = now − silence，不补积压]
  K -->|是| R[取 游标, now − silence 内普通群友未 @ 消息]
  R --> G[按人聚合 代表 = 最后一条]
  G --> G1{闸 1 抑制}
  G1 -->|管理员之后发过言 / 人工接待中 / 主流程已回复| X2[跳过此人]
  G1 -->|通过| G2{闸 2 可答性判断}
  G2 -->|false 或判断失败| X2
  G2 -->|true| G3{闸 3 主动模式推理}
  G3 -->|__NO_ANSWER__ / 空 / 出错| X2
  G3 -->|有答案| SEND[引用代表消息回复 + 记会话与 proactive_replies]
  1. S-00 全局开启或任一群单独开启时循环才扫描；逐群只处理 ProactiveOn 为真的群（4.6）。
  2. S-01 until = now − 该群静默阈值（ProactiveSilence：群策略 silenceSec 优先，否则全局）；无游标（群第一次被扫描）→ 游标设为 until 后结束（上线前的积压一律不补）；until ≤ 游标 → 结束。
  3. S-02 候选：(游标, until] 内 role NOT IN (owner, admin) AND NOT mentioned 的消息，按时间正序。
  4. S-03 按 user_id 聚合：同一人连发的多条以换行拼成一个问题，代表消息为其最后一条（回复引用它、提问时间取它）。
  5. S-04 闸 1 抑制：提问后群主 / 管理员发过言；该用户会话处于人工接待；该用户会话在提问后已有机器人或人工回复（主流程已答）。
  6. S-05 闸 2 可答性判断（30 秒超时，失败按不答）：只放行价格计费、功能用法、接入配置、规则政策、报错排查等可用知识库回答的问题；闲聊、情绪、群友对话、无关话题、订单账户事务（到账 / 退款 / 封禁）、操控指令一律 false。输出 {"answer": true|false}。
  7. S-06 闸 3 主动模式推理：不带历史、只给 kb_search 工具（不能转人工）；user 侧任务说明改为「仅当知识库检索到确切依据且你有把握时才作答；否则只输出 __NO_ANSWER__（不解释、不道歉、不引导人工或外链、不寒暄）」。system prompt 不变。
  8. S-07 补位：建 / 取该用户会话，把问题各条以 in 落库（代表消息带平台消息 ID），回复以 out 落库并发送（拆条规则同 FA-DD-004），记 proactive_replies。用量记 llm_calls.purpose = proactive。
  9. S-08 单群单轮最多补位 maxPerScan 人：达到上限时游标不前进，剩余的人下一轮处理（已答的人被闸 1 挡住）；未达上限则游标推进到 until。任一步数据库错误 → 游标不前进，下轮重试。

4.3 主动回复页（F-03）

  • 全局开关（写 proactive.enabled）、配置徽章（状态 / 静默阈值 / 扫描周期 / 单次上限）。全局关闭但有群单独开启时状态显示「部分群开启」。
  • 每群进度表：群、生效状态（不在白名单 / 已关闭 / 生效）、缓冲消息数、上次扫描、滞后（now − 该群静默阈值 − 游标）、主动回复数。
  • 最近 50 条主动回复，可标记「恰当 / 不当」（再点一次取消）。
  • QQ 未开启 groupAll 时顶部提示主动回复不会在 QQ 群生效。

4.4 入群欢迎（F-04）

  1. S-01 该群入群欢迎未开启（WelcomeOn：群策略优先，否则 welcome.enabled）、群不在白名单、或对应渠道的欢迎语为空 → 不发。
  2. S-02 模板：QQ 用 messageQq（格式由 formatQq 决定）、TG 用 messageTg（纯文本）。占位替换（renderWelcome）：
    占位QQ MarkdownQQ 纯文本 / TG
    {at}<qqbot-at-user id="{member_openid}" />（客户端显示 @昵称）昵称
    {name}事件昵称 → 同一用户最近出现过的昵称 → 「新朋友」（QQ 入群事件不带昵称，多数为「新朋友」）
    {brand}品牌名，空为「本群」
    {ask:问题}<qqbot-cmd-input text="…" show="…" reference="false" />（参数指令：点击把问题填进输入框；参数 urlencode）「问题」
  3. S-03 以主动消息发到群（无 ReplyTo）。QQ Markdown 发送体 {"msg_type":2,"markdown":{"content":…}}（群聊 / 单聊自定义 Markdown 自 2026-04-23 起对所有机器人开放，无需模板）。
  4. 后台「发送测试」：POST /api/welcome/test {channel, chatId, welcome} 按草稿（不必先保存）发到所选群，@ 该群最近发过言的用户；测试目标来自 GET /api/groups（会话表里出现过的群）。
  5. 后台内置五套 Markdown 样式预设（卡片 / 入口导航 / 简洁 / 快捷提问 / 群规公告）与近似 QQ 气泡的实时预览（web/src/components/welcome-editor.tsx）。QQ 客户端会把列表圆点单独排一行，预设一律用「每行一条 + emoji 开头」代替 Markdown 列表。模板与任一预设逐字一致时高亮该预设，否则标「当前：自定义模板」，套用预设前弹确认。缺省模板 = 卡片（settings.DefaultWelcomeQQ，与前端逐字一致，由 settings_test.go 校验）。
  6. 事件来源：QQ GROUP_MEMBER_ADD {group_openid, member_openid}；TG 消息的 new_chat_members（privacy mode 开着也能收到，跳过机器人账号）。

4.5 入群审核（F-05）

  1. S-00 该群入群审核未开启（JoinReviewOn）→ 不处理。
  2. S-01 事件 GROUP_JOIN_REQUEST：取 verify_info.verify_message 与 review_qa_list[].answer，trim 后按行拼成答案；auto_approved 存在表示平台策略已自动通过 → 只记录 auto。
  3. S-02 提取 ID：idPattern 外包「前后不紧贴字母数字」，取第一个匹配；无匹配或规则为空则取整段答案。答案为空 → 不调接口直接拒绝。
  4. S-03 核对：GET {checkUrl}?id=…（保留原 query），5 秒超时；只认 {"status":"ok"}（同意）/ {"status":"error"}（拒绝）。网络错误、超时、非 2xx、其他内容 → 记 pending，不审批，留给管理员在 QQ 里处理。
  5. S-04 审批：{"op":"approve"|"decline","join_request_id":…,"reject_reason":拒绝理由}；接口出错记 failed。
  6. S-05 每个申请记一行 join_requests（答案原文、提取 ID、结果、说明）。

4.6 按群设置 / 群管理页（F-07）

  1. S-01 设置分区 groups = {policies: [GroupPolicy]}。每条以 chat = 渠道:群ID 标识，proactive / welcome / joinReview / reflect / topics 为三态开关（null 跟随全局、true 单独开启、false 单独关闭），silenceSec 为 null 时用全局静默阈值，note 为后台备注。
  2. S-02 生效值：XxxOn(channel, chatId) = 群策略非 null ? 群策略 : 全局开关。单独开启覆盖全局关闭，反之亦然（群策略覆盖全局）。
  3. S-03 扫描器每轮先看 AnyXxx()（全局开启或任一群单独开启）决定要不要跑，再逐群过 XxxOn；QQ 群成员事件订阅条件改为 AnyWelcome() || AnyJoinReview()。
  4. S-04 校验：群标识须匹配 ^(qqbot|telegram|wecom):\S+$ 且不重复；备注不超过 64 字；静默阈值 0~86400；有任一群开启入群审核时也要求核对接口、有任一群开启欢迎时也做示例内容检查。
  5. S-05 保存：前端整体提交 PUT /api/settings {groups:{policies}}（分区级局部更新，其它分区不动）。Groups.UnmarshalJSON 每次解到全新切片——设置保存是「以当前值为底再覆盖」，复用旧切片会让旧元素里没出现在新 JSON 里的字段残留。全部跟随全局且无备注的策略不保存。系统设置页保存时不回写 groups，避免用打开页面时的旧值覆盖。
  6. S-06 群管理页列出「会话表里出现过的群 + 群时间线里的群 + 已有策略的群」，按最近消息倒序；每列显示该功能的生效值，单独设置的标品牌色圆点；不在白名单的群置灰。「按群 ID 添加」可给还没出现过的群预先设置。

4.7 问题排行（F-08 / F-09）

flowchart TD
  T[每 scanMin 分钟 且 AnyTopics] --> P[清理 retentionDays 之前的记录]
  P --> G[逐个白名单内、TopicsOn 的群]
  G --> B[取 游标, now − 2 分钟 内普通群友发言 ≤ windowMax 条]
  B --> F[去图片占位，少于 3 字的跳过]
  F --> L[askJSON：现有主题前 40 个 + 消息 JSONL]
  L --> R[校验并落到主题：topicId 归入 / newTitle 近义并入或新建 / noise 丢弃]
  R --> S[同一事务：写主题与出现记录 + 推进游标]
  S -->|批满 且 未满 5 批| B
  G --> PV[topics.enabled 时再处理私聊来源]
  1. S-01 来源：群时间线里 role NOT IN (owner, admin) 的发言（按群，游标 topic:{channel}:{chatId}，受群策略控制）；私聊（chat_type IN (private, guild_dm)，不含体验台）里客户发来的消息（游标 topic:private，只受全局开关控制）。群里 @ 机器人的消息已在时间线里，不重复取。
  2. S-02 静置 2 分钟（TopicSettle）再归类，等同一个人说完；冷启动从 7 天前开始；每来源每轮最多 5 批，积压分几轮追平；批未满即把游标推到 now − 2 分钟。
  3. S-03 归类提示词：只统计与本产品相关的咨询（接入配置、价格计费、账户事务、使用中的报错），通用编程、其他产品、闲聊寒暄一律 noise；拿不准算 noise；输出 {"items":[{"i":0,"topicId":3},{"i":1,"newTitle":"退款到账时间"},{"i":2,"noise":true}]}。用量记 purpose = topic。
  4. S-04 校验（resolveTopics）：越界 / 重复的序号丢弃；不在本次交给模型的主题清单里的 topicId（幻觉）丢弃；新标题截到 60 字，与现有主题（最近活跃的 500 个）或本批更早的新标题同名或近乎相同（kb.NearlySame）时并入，否则新建。
  5. S-05 落库（SaveTopicBatch）：新建主题（同名复用）、写出现记录、刷新主题活跃时间、推进游标在同一事务；模型调用或写库失败时游标不动，下一轮重跑同一批，不重复计数。
  6. S-06 排行：时间窗起点 = 浏览器时区下 days−1 天前的零点；按次数倒序取前 100，附人数、会话数、最近时间、上一个等长时间窗的次数（趋势：新 / 持平 / ±N），以及最近 3 条不同的原话。点主题看全部原话（分页 20）。
  7. S-07 管理：改名（与已有主题同名返回 409，提示改用合并）；合并（把 A 的全部记录并入 B 后删除 A）；删除（连同全部记录）。
  8. S-08 保留：出现记录保留 retentionDays 天；因此变空且之后没再被归入的主题一并删除。
