1. 概要

1.1 目的

群主 / 管理员在群里回答用户的内容本身就是最贴近实际的客服知识。反思沉淀把这些答复提炼成可复用 FAQ，立即进入机器人检索；定期合并近义条目，并把稳定、通用的条目升格为正式知识库文档。

1.2 范围

提炼扫描、判重、整理（近义合并）、升格评审、后台「反思沉淀」页的驳回 / 恢复 / 升格 / 立即整理 / 立即升格评审。

1.3 相关文档

FA-DD-008（群时间线、客服发言定义）、FA-DD-005（检索索引）。

1.4 用语定义

用语定义
沉淀条目kb_reflections 一行；approved 已入库（参与检索）/ rejected 已驳回 / promoted 已升格
沉降区间(游标, now − settleMin]：只评估这段时间内的客服发言
整理把 approved 条目分批交给模型做近义合并，整批替换
升格把一条 approved 条目写成知识库文档（标题「升格沉淀 #id」），条目转为 promoted、不再单独检索

2. 前提

2.1 系统构成

后台循环 RunReflector 每分钟醒一次：按 scanMin 执行提炼（与时间线清理）；整理、升格按各自周期检查是否到期（上次执行时间记在 poller_cursors 的 reflect_compact_at / reflect_promote_at，重启不丢）。提炼、整理、升格以及后台手动触发由同一把锁串行化。

2.2 技术要素

  • 三处模型调用都走 askJSON（FA-DD-008 2.2），超时 3 分钟；system 为固定提示词，聊天记录 / 已有知识 / 候选以 JSONL 放在 user 侧，所有字符串先剥伪造定界符。
  • 已有知识检索与判重用内存 BM25 索引：沉淀条目（approved）与文档块一起进入索引，来源名「人工沉淀」，命中结果带 reflectionId。

2.3 前提条件・制约事项

  • 素材只来自群时间线，QQ 需开启全量群消息（FA-DD-008 2.3）；否则时间线只有 @ 消息，群主的答复几乎进不来。
  • 判重不用向量，用 NearlySame（规范化相等、互相包含且都 ≥8 字、或 Jaccard ≥ 0.72）或与检索前 5 名的 bigram Jaccard ≥ 0.5；同义改写可能漏判，由整理环节兜底合并。
  • 沉淀通知不推送到群（无管理面），统一在后台审核。

4. 功能详细

4.1 提炼（F-01）

  1. S-01 对时间线里每个在白名单内的群：until = now − settleMin；无游标时游标取 now − lookbackMin；until ≤ 游标 → 跳过。
  2. S-02 (游标, until] 内没有客服发言 → 不调模型，游标推进到 until。
  3. S-03 窗口：游标前 10 条作上下文 + (游标, now] 内最多 windowMax 条（上界用 now，把区间后的追问 / 致谢也带上，作为答复有效的证据）。
  4. S-04 转成 JSONL {ts, role:"客服"|"用户", userId, text}；以窗口里 ≥4 字的消息为探针检索已有知识（全文前 2000 字 + 前 5 条各一次），合并去重取得分最高 6 条。
  5. S-05 调模型：只评估沉降区间内的客服发言是否有效回答了相邻问题；排除闲聊、猜测、隐私凭据、价格 / 倍率 / 可用性 / 公告 / 故障等时变事实；已被覆盖的不输出。返回 {"items":[{question, answer, effective, faq}]}。
  6. S-06 解析失败或调用出错 → 游标不前进，下一轮重试。
  7. S-07 对 effective=true 且 faq 非空的条目判重（2.3），不重复则写入 approved 并立即重建索引（同批后续条目的判重能看到它）。
  8. S-08 游标推进到 until。

4.2 整理（F-02）

  1. S-01 approved 条目数 < compactMinEntries → 不整理。
  2. S-02 按 id 升序每 30 条一批，不足 2 条的批次跳过。
  3. S-03 每批以条目为探针检索正式文档（不含沉淀条目）作冲突参照，调模型（提示词要点：激进近义合并、不得缩短、不得因文档已覆盖而删除、不得新增事实），返回 {"items":[{faq}]}。
  4. S-04 安全底线：结果非空；不超过输入 ×1.5；不少于 max(1, ⌈输入 ×0.4⌉)。不满足或调用失败 → 该批保持原样。
  5. S-05 只替换成功的批次：单事务删除这些条目、插入合并结果（compacted=true，无来源群与来源问答），并记一条 reflect_compactions（前后快照）。全部批次失败 → 报错，不改库。
  6. S-06 重建索引。无论结果如何都记下本次整理时间。

4.3 升格（F-03 / F-05）

  1. S-01 取最近 60 条 approved 条目为候选；不足 promoteMinEntries → 不评审。
  2. S-02 调模型（提示词偏保守，时变事实一律 false），返回 {"decisions":[{id, promote, reason}]}。
  3. S-03 只采纳候选内的 id、去重、最多 promoteMaxPerRun 条。
  4. S-04 逐条升格：单事务锁定条目（必须仍为 approved）→ 在知识库「反思沉淀」目录下新建文档「升格沉淀 #id」并切块 → 条目标 promoted、记 promoted_doc_id；重建索引。
  5. 后台单条「升格为正式文档」走同一 S-04。

4.4 后台页（F-04）

  • 配置与计数徽章：扫描周期、静置等待、整理周期、升格周期、已入库、可整理 / 门槛、已升格、已驳回。
  • 每群反思进度：缓冲消息、上次扫描、滞后（now − settle − 游标）、已沉淀条数；上次整理 / 升格评审时间。
  • 知识条目：按状态筛选；approved 可「升格为正式文档」「驳回」，rejected 可「恢复入库」，promoted 显示对应文档；可展开来源问答。
  • 「立即整理」需确认对话框；「立即整理」在已入库 < 门槛时禁用，「立即升格评审」在已入库 < 升格最少候选时禁用。
  • 整理记录：最近 10 次，展开查看整理前后全文。

HTTPmessage

400反思扫描间隔需在 1~1440 分钟之间（及 Validate 中其余 8 条区间校验，见 settings.Validate）

手动触发的结果文案：「{前} → {后} 条（共 n 批[，m 批失败保持原样]）」「条目不足 N 条，未整理」「评审 n 条，升格 #id → 文档 #id…」「评审 n 条，无升格」「候选不足 N 条，未评审」。
